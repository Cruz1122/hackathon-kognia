# Commercial Analytics Implementation Spec (Temporary)

> Working specification for the commercial analytics delivery. Keep this file
> next to the implementation while the feature is being completed; remove or
> promote it to permanent documentation once the final audit is complete.

## Objective

Implement the minimum commercial data model, deterministic analytics, Redis
cache and queue, enrichment worker, recovery attribution, analytics API,
frontend dashboard, and agent tool. Do not perform a general
re-architecture.

Priorities: simplicity, maintainability, fast queries, correct multi-tenancy,
deterministic analytics, useful Redis, no unnecessary redundancy, and no
over-engineering.

Each phase must be implemented, tested, and adversarially validated before the
next phase. The required validator is `némesis.tester`; it is currently not
available in this environment, so any substitute result must be reported as a
limitation rather than a PASS.

## Existing System and Target Flow

The existing stack is FastAPI, async SQLAlchemy/asyncpg, Alembic, PostgreSQL,
JWT auth, organization tenancy, WebSockets, in-memory realtime, RAG/Chroma,
Sherpa STT, Piper TTS, Astro 7, TypeScript, Vite, and pnpm.

Existing entities are `organizations`, `users`, `conversations`, and
`messages`. The target minimum flow is:

```text
customer
    ↓
conversation
    ├── voice call
    └── WhatsApp continuation
           ↓
      opportunity
           ↓
     won / lost / pending
```

Do not create a full CRM or redundant `Sale` entity.

## Mandatory Architecture

Keep a modular FastAPI monolith plus a second worker process, PostgreSQL, and
Redis. Reuse the backend image:

```text
backend: uvicorn app.main:app
worker:  python -m app.worker
```

PostgreSQL is the only business source of truth. The LLM may extract
conversation signals but never calculates metrics, money, or commercial
outcomes. Analytics are SQL-derived. Redis is used only for analytics cache
and the minimal worker queue.

Do not add Celery, RQ, RabbitMQ, Kafka, Temporal, Airflow, materialized views,
aggregate tables, L1 cache, a generic analytics ORM, SQL generated by an LLM,
an analytics database, CQRS, event sourcing, GraphQL, Kubernetes, or
enterprise observability.

## Metrics and Definitions

The API must support conversations, won sales, conversion rate, revenue,
recovered sales, recovery rate, recovered revenue, lost reasons, objection
resolution, and product interest-to-conversion.

- Conversations: count organization-scoped conversations in `[from, to)`.
- Won: `COUNT(opportunities WHERE status = 'won')`.
- Conversion: `won / total opportunities * 100`; never use messages as the
  denominator.
- Revenue: `SUM(amount_minor)` for won opportunities. Store money as integer
  minor units; never use floating point for money.
- Recovered: `recovery_started_at IS NOT NULL AND recovered_at IS NOT NULL AND
  status = 'won'`.
- Recovery rate: recovered won opportunities divided by opportunities with
  `recovery_started_at`.
- Recovered revenue: won opportunities with `recovered_at IS NOT NULL`.
- Lost reasons: `lost_reason` distribution for lost opportunities only.
- Objection resolution: resolved objections divided by total objections.
- Product conversion: per product, return `product_id`, `product_name`,
  `interested_count`, `won_count`, and `conversion_rate`.

All denominators must handle zero and all queries must be tenant- and
date-scoped where applicable.

## Phase 1 — Minimum Commercial Model

Create one clean Alembic migration and matching SQLAlchemy models. Do not edit
old migrations. Preserve existing data and conversation compatibility.

### Entities

- `Customer`: `id`, `organization_id`, nullable `name`, nullable `phone`,
  `created_at`, `updated_at`; indexes on organization and
  `(organization_id, phone)`.
- `Conversation`: add nullable `customer_id`; preserve the existing
  `channel` field.
- `Message`: add `channel`, initially `voice`, `whatsapp`, or `system`, with a
  compatibility default.
- `Call`: `id`, `organization_id`, `conversation_id`, `started_at`, nullable
  `ended_at`, `status` (`active`, `ended`, `failed`), `created_at`, and optional
  `external_id`; indexes on `(organization_id, started_at)` and
  `conversation_id`.
- `Product`: `id`, `organization_id`, `name`, `active`, `created_at`, unique
  `(organization_id, name)`.
- `Opportunity`: `id`, `organization_id`, `conversation_id`, nullable
  `customer_id` and `product_id`, `status` (`pending`, `won`, `lost`), nullable
  integer `amount_minor`, `currency`, nullable `lost_reason`, recovery fields,
  won/lost timestamps, and created/updated timestamps. Enforce non-negative
  money, status/timestamp consistency, recovery ordering, tenant-scoped
  relationships, and the required organization/status/date,
  conversation, and product indexes.
- `Objection`: `id`, `organization_id`, `conversation_id`, normalized text
  `category`, `resolved`, `created_at`, nullable `resolved_at`; required
  organization/date, category, and conversation indexes.
- `ProductInterest`: `id`, `organization_id`, `conversation_id`, `product_id`,
  `created_at`; unique `(conversation_id, product_id)` plus required indexes.

Every commercial relationship must prevent cross-tenant references.

## Phase 2 — Redis and Minimal Worker

Add configurable `REDIS_URL` and `ANALYTICS_CACHE_TTL_SECONDS` (default 60), an
internal-only official Redis Compose service with healthcheck, and a worker
using the backend image. Keep one small Redis adapter with client, ping, and
close behavior.

Implement a JSON Redis queue for `enrich_conversation` jobs:

```json
{
  "type": "enrich_conversation",
  "organization_id": "...",
  "conversation_id": "..."
}
```

The worker validates payloads, handles jobs, logs failures, continues after
bad jobs, and shuts down gracefully. Redis failure must not break commercial
operations or PostgreSQL-backed analytics.

Transient job failures are requeued with a bounded three-attempt counter;
permanently failing jobs are logged and discarded rather than introducing a
dead-letter subsystem.

Validate Redis connectivity, enqueue/dequeue, worker processing, invalid
payload handling, Redis failure behavior, Compose health, client cleanup, and
CPU behavior. Do not add a job framework, priorities, scheduling, dashboards,
or orchestration.

## Phase 3 — Deterministic SQL Analytics and Cache

Create a small `backend/app/analytics/` module with repository, service,
schemas, and cache. Repository methods accept tenant and date boundaries,
use explicit SQL aggregation (`COUNT`, `SUM`, `GROUP BY`, `CASE`, joins), and
avoid N+1 queries, transcript loading, and ORM loops over large datasets.

Use a single typed dashboard payload containing period, summary, conversion
trend, lost reasons, objections, and products. Never return money as float.

Use cache-aside Redis with organization versioning and TTL. The authoritative
organization revision lives in PostgreSQL and is included in the Redis cache
key; this prevents stale analytics when a mutation commits while Redis is
unavailable. Cache invalidation must not use `KEYS` or global scans.
PostgreSQL remains authoritative, including when Redis is down. Reading the
small organization revision is allowed on a cache lookup; a cache hit must not
run the analytics aggregation queries.

Validate every metric with controlled fixtures, zero denominators, date
boundaries, tenant isolation, cache hit/miss, invalidation, Redis fallback,
query plans where useful, and absence of N+1 or revenue duplication.

## Phase 4 — Conversation Enrichment and Recovery

When a real call changes to `ended`, enqueue one idempotent enrichment job.
Load only tenant-scoped messages, known products, and relevant opportunity
context. Validate LLM output with Pydantic. Reject unknown or cross-tenant
product IDs. The LLM may extract lost reason, objections, and product
interest, but may not set commercial status or invent revenue.

Re-enrichment replaces only derived objections, never manual data, and does not
duplicate product interests. Persist `lost_reason` only for an already lost
opportunity. Recovery starts on the existing opportunity with
`recovery_started_at` and `recovery_channel = 'whatsapp'`; when that same
opportunity becomes won, set `recovered_at`. Do not create a second
opportunity. If no real WhatsApp provider exists, leave a clear domain hook;
do not fabricate an integration.

Validate enqueue behavior, retries, idempotency, invalid structured output,
tenant-safe products, derived-data replacement, recovery attribution, same
opportunity behavior, and analytics invalidation.

## Phase 5 — Analytics API

Register a dedicated analytics router from `main.py` with:

```text
GET /analytics/dashboard?from=...&to=...
```

Require existing auth, derive organization only from the authenticated user,
return one stable Pydantic payload, support empty data and invalid dates, and
preserve existing tenant semantics. Validate auth, tenant isolation, ranges,
empty data, complete payload, cache behavior, Redis fallback, and stale-cache
behavior after mutation.

## Phase 6 — Astro Dashboard

Implement the final Astro page against the real dashboard API. Remove dummy
analytics data. Preserve the approved warm graphite/amber/cream visual
language, Urbanist, mostly white cards, restrained corner radii, clean charts,
and desktop-first responsive behavior.

Show the main KPIs (revenue, won, conversion, recovered revenue), secondary
KPIs (conversations, recovered sales, recovery rate), and only useful charts:
conversion trend, lost reasons, objections, product interest-to-conversion,
and recovery. Implement explicit loading, success, empty, and error states;
do not show fake zeroes while loading.

Run `pnpm test` and `pnpm run build`, then validate API usage, formatting,
responsive behavior, console errors, visual consistency, and absence of dummy
data.

## Phase 7 — Agent Tool

Add one `get_business_analytics` tool to the existing agent. It calls
`AnalyticsService`, validates `date_from`, `date_to`, and an optional selector
(`overview`, `recovery`, `losses`, `products`, `objections`), preserves tenant
context, and does not accept SQL, table names, or query fragments. The model
interprets the typed result; it must not recalculate authoritative metrics.

Validate tool registration, tenant isolation, input errors, service reuse, no
SQL generated by the LLM, and error handling that does not break the agent.

## Phase 8 — Final E2E and Performance Sanity

Run PostgreSQL, Redis, Chroma, backend, worker, and frontend. Apply migrations
from a clean state. Exercise Organization A with customer, conversation,
call, pending opportunity, product interest, objection, call completion,
enrichment, WhatsApp recovery, won transition, and dashboard verification.
Exercise Organization B separately and prove no analytics leakage.

Controlled expected fixture:

```text

4 won
6 lost
2 recovery_started
1 recovered won
won revenue = 100 + 200 + 300 + 400 = 1000
recovered revenue = 400

won = 4
conversion = 40%
recovered_sales = 1
recovery_rate = 50%

Check for N+1, explosive joins, absurd scans, cache effectiveness, and

```

## Final Adversarial Audit

Invoke `némesis.tester` with the complete implementation. It must inspect
code, migrations, Redis, worker, queries, API, frontend, and agent tool and
look for cross-tenant leaks, duplicated revenue, incorrect conversion or

as source of truth, dead workers, shutdown issues, irreversible migrations,
dummy UI data, inconsistent UI/API metrics, regressions, redundancy, and
unrequested features. Run all available backend, frontend, Compose, and build
checks. The final result is complete only with:

```text
NÉMESIS FINAL: PASS
```
